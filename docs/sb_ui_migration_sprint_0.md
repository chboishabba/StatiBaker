# Sprint 0: SB UI Migration (Contracts + SvelteKit Scaffold)

Status: proposed

This sprint is the concrete next step from the current state (Python emits
`dashboard*.json` + legacy static HTML from `sb/dashboard.py`) to the planned
Svelte component UI described in `docs/svelte_migration_sprint.md`.

## Current State (Baseline)

- UI is generated by Python renderers in `sb/dashboard.py`:
  - JSON: `runs/<date>/outputs/dashboard*.json`
  - HTML: `runs/<date>/outputs/dashboard*.html`
- Tests exercise the Python compile path, not any frontend app:
  - `tests/test_dashboard.py` calls `build_dashboard`, `build_weekly_dashboard`,
    `build_lifetime_dashboard`.
- There is no `frontend/sb-dashboard` SvelteKit project in-tree yet.

## Goal

Create a real, runnable SvelteKit app that:
- loads an existing real `dashboard*.json` (daily first),
- validates the payload shape (runtime),
- renders a minimal-but-structured page from that payload,
- without changing the SB pipeline semantics.

This sprint is explicitly about getting the UI lane "exercised" for the first
time, under contract discipline.

## Non-Goals

- No replacement/removal of legacy HTML output yet.
- No UI polish, no full parity, no weekly/lifetime routes unless time remains.
- No daemon/web-control-plane integration (that is separate work).
- No changes to SB epistemic boundaries (meta-only, append-only, no promotion).

## Deliverables

1. **Dashboard payload contract lock**
   - Add a machine-readable schema for the daily dashboard payload:
     - Proposed file: `StatiBaker/DASHBOARD_SCHEMA.json`
   - Add a visible payload version field emitted by the compiler:
     - Proposed key: `payload_version` (string), e.g. `"dashboard.v1"`
   - Add a short “contract notes” section to `docs/web_module_map.md` if needed:
     - which keys are stable for the UI to rely on
     - compatibility rules when adding/removing fields

2. **Payload fixtures (for UI and contract tests)**
   - Add a fixture directory with real-ish payload samples:
     - Proposed path: `StatiBaker/fixtures/dashboard_payloads/`
     - `daily.dashboard.json` (from a real run)
     - Optional: `weekly.dashboard_weekly.json`, `lifetime.dashboard_lifetime.json`
   - Document a deterministic way to refresh fixtures:
     - Which `--date` to use
     - Which compiler flags/modes are required (debug vs scoped)

3. **SvelteKit scaffold that can load real SB outputs**
   - Create `StatiBaker/frontend/sb-dashboard/` with:
     - SvelteKit app
     - Tailwind (optional in sprint 0; OK to defer)
     - `zod` for runtime validation (or JSON schema validation if preferred)
   - Provide one command surface:
     - `npm install`
     - `npm run dev`

4. **Minimal daily page**
   - Route: `/daily/[date]`
   - Data loading strategy (pick one for sprint 0, keep it simple):
     - Option A (recommended): SvelteKit server route reads JSON from
       `../runs/<date>/outputs/dashboard.json` and returns it.
     - Option B: Copy fixture JSON into app `static/` for first load, then add
       real runs path in sprint 1.
   - Render minimal sections driven directly by JSON keys:
     - Header (date, generated_at)
     - Summary cards (whatever exists in `summary`)
     - Frequency by hour (simple table)
     - Timeline list (collapsed; no filtering yet)
   - Error behavior:
     - If validation fails, show an explicit contract error panel with the first
       N validation issues.

## Acceptance Criteria (Sprint 0 Complete)

- A SvelteKit dev server can render a real daily dashboard for at least one
  `runs/<date>/outputs/dashboard.json` without manual JSON edits.
- The app validates the payload and fails with a clear error page when the JSON
  shape breaks.
- The daily view renders at least: header, summary, frequency-by-hour, timeline.
- Legacy Python HTML remains unchanged and still builds.

## Risks / Known Tricky Bits

- Reading local `runs/` files from a browser requires a server:
  - handle via SvelteKit server-side routes (recommended), not direct filesystem
    fetch from client JS.
- Contract drift is the main failure mode:
  - schema + fixtures + validation gate are the control points.
